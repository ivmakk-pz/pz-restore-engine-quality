# Build 42.20 compatibility audit

Status: in-progress - static analysis and SP/MP testing both clean on 42.20; the user-reported MP breakage did not reproduce (see "Field report"), and three test cases remain uncovered

Goal: record the static compatibility check of the mod against PZ build 42.20.0, so that if an issue turns up in-game we already know which engine APIs were inspected, what changed underneath them, and which areas were flagged as behavioural-risk rather than breaking.

Date: 2026-07-30. Mod version at time of audit: 1.2.1 (`versionMin=42.17`, single `42/` content folder). Last known-good tested build: 42.19.0 (SP + MP).

## Verdict

Static analysis: no code changes required for 42.20. All engine APIs the mod calls survived the vehicle refactor and the security lockdown. Two behavioural changes are worth knowing about but neither requires an edit.

A field report of MP breakage on 42.20 (below) prompted a full repro attempt. **It did not reproduce**: SP and two instrumented dedicated-server runs - one vanilla vehicle, one modded - all completed cleanly with correct numbers. The report remains unexplained rather than disproved, since the reporter's exact conditions (hosted co-op, their mod list, their mod version) were not reproduced. See "Verification status" for what is and is not covered.

## Findings

### 1. Vehicle refactor - the main risk area, no breakage

42.20 split `BaseVehicle` apart (855 insertions / 884 deletions) into `VehicleEngine`, `VehicleParts`, `VehiclePartOwner`, `VehicleAlarm`, `VirtualVehicle`. Every method the mod uses is still on `BaseVehicle` as a thin delegate with identical semantics:

| Mod call site | 42.20 state |
|---|---|
| `vehicle:setEngineFeature(q, l, p)` | `BaseVehicle.java:8115` -> `getVehicleEngine().setFeatures(...)` |
| `vehicle:getEngineQuality()` | `BaseVehicle.java:8120` -> `VehicleEngine.getQuality()` |
| `vehicle:getEngineLoudness()` | `BaseVehicle.java:8124` -> `VehicleEngine.getLoudness()` |
| `vehicle:getEnginePower()` | `BaseVehicle.java:8128` -> `VehicleEngine.getPower()` |
| `vehicle:transmitEngine()` | `BaseVehicle.java:9184`, unchanged body |
| `vehicle:getPartById(id)` | delegates to `VehicleParts.getPartById` (`VehicleParts.java:113`) |
| `part:getVehicle()` | kept, now `Type.tryCastTo(this.vehicle, BaseVehicle.class)` (`VehiclePart.java`) |

Loudness round-trip is preserved. Old: `this.engineLoudness = (int)(loudness / 2.7F)`. New (`VehicleEngine.java:83-87`): `this.loudness = (int)(loudness * 0.37037036F)`. Same value, so `REQ_RestorationPlan.calculateLoudnessFeature`'s `(target + 0.9) * 2.7` inverse still holds.

`VehiclePart.vehicle` was retyped from `BaseVehicle` to the new `VehiclePartOwner` interface, and `getOwner()` was added. `getVehicle()` was kept for compatibility and returns null only when the owner is a `VirtualVehicle` (an out-of-loaded-area vehicle). A `VirtualVehicle` cannot be the target of the mechanics UI, so the mod's unguarded `part:getVehicle():getEngineQuality()` in `REQ_ISVehicleMechanics.lua:65` is not reachable with a nil vehicle. **If an in-game nil-index error ever appears there, this is the first thing to re-check.**

### 2. Security lockdown - not applicable to this mod

42.20 is the most breaking release of the 42.x line for mods: reflection globals now throw outside debug, `getFileWriter` is extension-whitelisted, `getSandboxFileWriter` and the transaction globals were removed, `LuaManager` is `@HiddenFromLua` wholesale. Grepped the full mod source for `getClassField`, `getClassFunction`, `getNumClass*`, `getMethodParameter*`, `getFileWriter`, `getSandboxFileWriter`, `createItemTransaction`, `changeItemTypeTransaction`, `getRadioTranslators`, `getTranslatorCredits`, `requestMedicalCheck`, `sendFaction*`, `acceptFaction*` - zero hits.

The only `LuaManager` exposer changes were to those reflection globals; normal Java method exposure is untouched, so `setEngineFeature` remains callable from Lua despite now being an interface `@Override`.

### 3. Context-menu hook intact

`ISVehicleMechanics:doPartContextMenu(part, x, y)` signature is unchanged (`ISVehicleMechanics.lua:208`). The file's only 42.20 edit is inside `doMenuTooltip` (item-name dedup for the one-of list), which the mod does not patch. Also verified unchanged: `ISVehicleMenu.onExit`, `ISVehiclePartMenu.toPlayerInventory`, `VehicleUtils.getItems`, `VehicleUtils.RequiredKeyNotFound`, `ItemTag.WRENCH`, `ISOpenVehicleDoor` / `ISCloseVehicleDoor` / `ISUnlockVehicleDoor`, `ISPathFindAction:pathToVehicleArea`, `ItemContainer.getFirstTagEvalRecurse` / `getNumberOfItem` / `containsTypeRecurse` / `getFirstTypeRecurse`.

Translation keys the mod borrows from vanilla still exist: `IGUI_Vehicle_EngineQuality` (`IG_UI.json:1484`), `IGUI_RepairEngine` (`IG_UI.json:1510`).

`PZAPI/ModOptions.lua` has no diff between the two builds, so `REQ_ModOptions` is unaffected.

### 4. MP path unchanged

- `IsoObjectChange.MECHANIC_ACTION_DONE` encode/decode in `IsoGameCharacter.java` is byte-identical to 42.19 (send: `bb.putBoolean(tbl.rawget("success"))`; receive: triggers `OnMechanicActionDone`).
- `transmitEngine()` still just sets the `updateFlags | 4` bit server-side.
- The engine-sync packet still calls `getVehicle():setEngineFeature(bb.getInt(), bb.getInt(), bb.getInt())`.
- The global-timed-action requirement from ticket `plan-fixMPCompletionHang.md` is unaffected; `ISRestoreEngineQuality = REQ_ISRestoreEngineQuality` (`REQ_ISRestoreEngineQuality.lua:19`) is still the load-bearing line for MP reconstruction.

### 5. Vanilla engine-creation formula unchanged

`Vehicles.Create.Engine` (`server/Vehicles/Vehicles.lua:262-288`) is untouched, so `REQ_RestorationPlan.calculateNewEnginePower`'s mirror of it (`quality * 1.6` capped at 100, `math.max(0.6, boosted/100)` modifier applied to `getScript():getEngineForce()`) still matches vanilla.

## Behavioural changes to watch in-game (not breakage)

**Engine power now actually drives the car.** The vehicle controller switched from `getScript().getEngineForce()` to `vehicleObject.getEnginePower()` when computing drive force. This is the patch-note line "Fixed vehicle engine power being incorrectly set to the maximum script value instead of its calculated value". Consequence for this mod: the power value written by `setEngineFeature` used to be near-cosmetic for acceleration and is now the real input. The mod already writes a correctly-scaled value, so the expected outcome is that restoring quality produces a *noticeable* acceleration gain where before it did not. If a player reports a car feeling wrong (too fast, too slow, or unchanged) after restoration, this is the cause to investigate first.

**Timed actions are blocked while dragging a corpse.** `ISTimedActionQueue.add` / `addAfter` now silently reject any action without `allowedWhileDraggingCorpses = true`, showing `IGUI_CantDoWhileDragging` halo text instead. Vanilla vehicle-mechanic actions did not get the flag either, so the mod is at parity with vanilla - but if a player reports "clicking restore does nothing", ask whether they were dragging a corpse. Setting the flag on `REQ_ISRestoreEngineQuality` would be the fix if we decide to diverge from vanilla.

## Field report: MP broken on 42.20

Workshop comment, AlzaboHD, 2 Aug:

> Unfortunately does not work on 42.20 MP
>
> Causes stuck looping animation when interacting with car mechanics and other errors.

Unknowns in the report: which mod version they run (1.2.1 vs an older cached copy), hosted vs dedicated server, whether other mods are installed, and what "other errors" were. No log excerpt was provided. "Stuck looping animation" is the same symptom class as the bug fixed in 1.2.1 (`plan-fixMPCompletionHang.md`): the client plays the action animation while waiting for a server completion signal that never arrives.

### Ruled out by this audit

These were checked against the 42.19 -> 42.20 diff and are *not* the cause:

- **The MP net-transaction path.** `NetTimedAction` and `NetTimedActionPacket` have no diff at all. `LuaTimedActionNew.java` changed only by adding two nil-guards around `failedPathfind` / `succeededPathfind` callbacks - no change to the reconstruct-by-global-name flow or to the `useCustomRemoteTimedActionSync` decision.
- **`IsoObjectChange.MECHANIC_ACTION_DONE`** encode/decode: byte-identical.
- **Every engine and part API the mod calls** (findings 1 and 3 above).
- **`getEngineQuality()` returning 0 on an engine-less vehicle.** The new `getEngine() == null ? 0 : ...` guard looks like a behaviour change, but `VehicleParts.getEngine()` returns the Engine *VehiclePart* (registered from the vehicle script at `VehicleParts.java:92-94`), not the installed inventory item. The part exists whenever the vehicle script defines one, so quality still reads its real stored value.
- **`ItemTag.WRENCH`, `VehicleUtils.RequiredKeyNotFound`, `VehicleUtils.getItems`** - all unchanged, so the requirement checks the server re-runs in `isValid()` have the same inputs as on 42.19.

### Candidate causes, roughly by priority

1. **Server-side error inside `isValid()` / `complete()`.** `REQ_ISRestoreEngineQuality:isValid()` calls `REQ_Requirements.validateAllRequirements`, which calls `getText`, `getItemDisplayName("Base.EngineParts")`, and `VehicleUtils.RequiredKeyNotFound` - all evaluated **server-side** on the reconstructed action. If any of those now throws or returns unexpectedly under the 42.20 server, the action never reports done and the client animation loops forever. Nothing in the diff explains it, but this is the code path whose failure produces exactly the reported symptom, so it is where to instrument first. Note `REQ_ModOptions` is required from `shared/` while `PZAPI/ModOptions.lua` is `client/`-only - the `or 2` fallback in `REQ_ModOptions.getEnginePartsPerIteration()` is what keeps this working server-side, and any change there would be silent.
2. **The `ISRestoreEngineQuality` global not being defined server-side.** The 1.2.1 fix depends on `shared/REQ_ISRestoreEngineQuality.lua` being loaded (and its global assigned) on the server. Confirm from the server log that the file loaded, rather than assuming it.
3. **Mod conflict or a stale mod copy on the reporter's server.** "Other errors" plus "interacting with car mechanics" generally could mean another mod also patching `ISVehicleMechanics`, or the server running a pre-1.2.1 copy where the MP hang is the known, already-fixed bug. Worth asking for `DebugLog-server.txt` and their mod list before assuming a 42.20 regression.
4. **A vanilla 42.20 MP regression in the mechanics UI itself.** Reproduce with the mod disabled to establish the baseline before attributing anything to the mod.

### Observations from the instrumented runs

**The client action ends via `stop`, not `perform`.** Both runs end `[CLI] isValid: false, unmet: Spare Engine Parts` then `[CLI] stop (action cancelled)`. The action consumes every available EngineParts in one go, so the "at least `partsPerIteration` parts" requirement fails immediately afterwards and the queue cancels the action instead of performing it. Harmless in these runs, but a cancelled action can make `ISTimedActionQueue` drop the remainder of the queue - and on the hood-closed path `ISCloseVehicleDoor` is queued *after* the restore. That combination is untested and is the most plausible remaining defect.

**Server-side `isValid()` never runs.** The server log carries only `new` and `complete` breadcrumbs, no `validateAllRequirements` steps. So the server reconstructs the action and executes `complete()` without re-validating requirements; all validation is client-side.

**Power saturates at 63% quality.** Vanilla's formula caps `quality * 1.6` at 100, so any quality at or above 63 yields full engine force. Now that 42.20 routes drive force through `getEnginePower()`, restoring beyond ~63% buys no further acceleration - only the quality and loudness numbers keep moving.

### Non-mod log noise seen during testing

- `AdvancedAnimator$1.visitFileFailed > NoSuchFileException ...\media\{AnimSets,actiongroups}` - the server scans every mod for optional animation folders. Fires for `RestoreEngineQuality`, `91range` and `damnlib` alike. Benign.
- `ImportedSkeleton.collectBoneFrames > Could not find bone index for node name: "Body"` - KI5 vehicle models. Absent before `91range` was installed.
- `IsoChunk.LoadOrCreate > SANITY CHECK FAIL` (CRC mismatch, chunks near 1035,1535) - appeared only in the 13:51 run, zero in earlier runs. World-save chunk integrity, unrelated to vehicle mechanics. Regenerate the test world if it recurs.

### Test scaffolding used

Engine state is server-authoritative and `BaseVehicle.transmitEngine()` is a no-op unless `GameServer.server`, so a client cannot lower engine quality for testing - a client-side `setEngineFeature` + `transmitEngine` silently does nothing in MP (this is not new in 42.20; the guard is unchanged from 42.19, such snippets only ever worked in SP). A `REQDebugTools` helper mod handles a `sendClientCommand(player, "REQDebug", "setEngineQuality", {quality = N})` on the server instead. It lives at `dev/REQDebugTools` in this repo (outside `Contents/`, so it never ships) and is staged to `Zomboid\mods\REQDebugTools` for use - see `dev/README.md` for setup and the loudness-scaling caveat. Remove it from `servertest.ini` `Mods=` for any run whose results need to be trustworthy - it is an unauthenticated command any client could call.

## If something breaks in game

Ordered by likelihood given the above:

1. MP looping animation / hang -> see the field-report section; start with the server DebugLog and the `isValid()` path.
2. Nil vehicle from `part:getVehicle()` -> `VirtualVehicle` owner (finding 1). Would show as a nil-index error in `REQ_ISVehicleMechanics.lua:65` or `REQ_RestorationPlan.lua:87`.
3. Acceleration behaving unexpectedly -> engine power is now load-bearing (behavioural change 1).
4. Restore option doing nothing on click -> corpse-dragging queue rejection (behavioural change 2).

Enable `DEBUG_MODE` in `REQ_Utils.lua` before reproducing, otherwise the `pcall` around `REQ_ISVehicleMechanics.initialize()` swallows the trace.
