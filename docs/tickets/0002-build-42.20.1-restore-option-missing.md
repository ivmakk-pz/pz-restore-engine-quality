# Build 42.20.1 compatibility audit - "Restore option missing" report

Status: not reproduced - static analysis clean AND verified working in English SP + MP and Ukrainian SP with a clean log (see "Verification"). One Workshop report, reporter untested; leading remaining cause is the reporter's specific setup (a language whose vanilla files 42.20.1 missed, another mod's translation, or environment) surfacing the 42.20.1 getText strictness regression.

Goal: audit the mod against the 42.20.1 hotfix after a player reported the restore option no longer appearing, identify whether 42.20.1 introduces a real regression in the mod's code path, and record what was inspected so an in-game repro has a head start.

Date: 2026-08-05. Mod version: 1.2.1 (`versionMin=42.17`, single `42/` content folder). Prior audit (`0001-build-42.20-compatibility-audit.md`) cleared 42.17 -> 42.20.0 in SP and MP. This ticket covers only the 42.20.0 -> 42.20.1 delta.

> B42.20.01 hotfix seems to have broken this mod. When I right click on the engine, it doesn't show the option to restore the engine quality.

Unknowns: SP vs MP, game language, other mods installed, whether the mod is actually enabled/up to date. Reporter has not confirmed a repro.

## Verdict (static)

The mod's own menu-building path is compatible with 42.20.1. Nothing in the hotfix changes the context-menu hook, the vehicle/engine APIs, or any translation key the mod references. In English the restore option should still build and appear.

42.20.1 does contain one genuinely breaking-shaped change - a `getText` rewrite that now throws an uncaught exception on any translation value carrying a stray `%`. The mod's own strings and the vanilla keys it borrows are all `%`-free, so this does not trip the mod in English. It remains the single most plausible mechanism behind the report, but only via a non-English locale or another mod's translation, not via this mod's code. Needs in-game repro to confirm.

## What changed in 42.20.1 (mod-relevant)

Client Lua diff is tiny and untouching: `ISVehicleMechanics.lua` (the hook target) has **no diff**; `ISVehicleMenu.lua` changed only two towing-menu `getText` calls. Java side:

- `BaseVehicle.java`: removed one unused field (`connectionState[]`). No method the mod calls changed.
- `LuaManager.java`: collapsed the `getText` / `getTextOrNull` Lua exposers from many fixed-arity overloads into a single varargs `getText(String, Object...)` -> `Translator.getText(txt, args)`. Also removed `getRadioText` and added `deleteDatabase`, `.json` to the `getFileWriter` extension whitelist - none used by the mod.
- `Translator.java` (largest change, 180 lines): the percent-symbol handling fix.

### The getText mechanism (the one to understand)

Before 42.20.1, Lua `getText("KEY")` bound to a dedicated no-format overload (`Translator.getText(String)`) that returned the raw translation verbatim - a literal `%` passed through untouched.

After 42.20.1 there is only `getText(String desc, Object... args)`:

```java
public static String getText(String desc, Object... args) {
    return reportMissingArgumentsFromPastAbuse(desc, args, getTextInternal(desc, false));
}
private static String reportMissingArgumentsFromPastAbuse(String desc, Object[] args, String text) {
    try {
        return text.formatted(fixupArgs(args));   // ALWAYS runs String.format now
    } catch (MissingFormatArgumentException var4) { // only THIS subclass is caught
        ...
        return text;
    }
}
```

So every `getText("KEY")` from Lua now runs Java `String.formatted()` on the result. `String.format` throws `IllegalFormatException` on any `%` that is not a valid `%%` or `%1`..`%9` token (e.g. a lone `50%`). The catch only covers `MissingFormatArgumentException`; siblings like `UnknownFormatConversionException` / `IllegalFormatConversionException` propagate **uncaught** into Lua and error the calling function.

The game escaped its own English translation files to compensate (the bulk of the 42.20.1 diff is `%` -> `%%` across vanilla `Translate/*/…json`, plus a load-time `formatFixer` that rewrites `%%`->`%%` and `%1`->`%1$s`). English vanilla is therefore safe. The risk lives wherever a translation value still holds an unescaped lone `%`: a language file the fix missed, or a third-party mod's translations.

## Why the mod's own path is clean

`REQ_ISVehicleMechanics.extendedDoPartContextMenu` (`REQ_ISVehicleMechanics.lua:57`) calls the vanilla original first (line 60), then for the Engine part runs, in order, before `addOption` (line 76):

1. `part:getVehicle():getEngineQuality()` (line 65) - unchanged API.
2. `REQ_Requirements.validateAllRequirements` (line 69) - calls `getText("IGUI_perks_Mechanics")`, `getItemDisplayName("Base.Wrench")`, `getItemDisplayName("Base.EngineParts")`, `getText("Tooltip_vehicle_keyRequired")`.
3. `REQ_RestorationPlan.calculateFromGameState` (line 72) - math + mod-option read, no `getText`.
4. `REQ_ISVehicleMechanics.generateMenuText` (line 75) - `getText("IGUI_REQ_Restore")`, `getText("IGUI_Vehicle_EngineQuality")`.

Every key resolves to a `%`-free value in EN:

| Key | EN value |
|---|---|
| `IGUI_perks_Mechanics` | `Mechanics` |
| `Tooltip_vehicle_keyRequired` | `Car Key is required` |
| `IGUI_Vehicle_EngineQuality` | `Engine Quality:` |
| `IGUI_REQ_Restore` / `IGUI_REQ_*` | mod's own EN files, no `%` |

`getItemDisplayName` uses a separate path (`getDisplayItemName`), not the reformatted `getText`. The mod's own `Translate/EN/*.json` contain no `%` at all. A grep of the vanilla EN `Translate/` for a remaining unescaped lone `%` returned nothing. So in English, step 2 and step 4 cannot throw from the getText change, and the option is added normally.

Note the tooltip `%` signs the mod shows in-game (`REQ_Tooltips.lua:89,105`, e.g. `(+5%)`) are plain Lua string concatenation, never passed through `getText`, so the Translator change does not touch them.

## Leading hypotheses for the report

1. **Non-English locale.** If the reporter runs a language whose vanilla `Tooltip.json` / `IG_UI.json` still holds an unescaped `%` in a key the vehicle part-menu build touches, the vanilla `originalDoPartContextMenu` call at line 60 (or one of our borrowed keys in that language) throws inside `getText`, aborting `extendedDoPartContextMenu` before `addOption`. Result: vanilla part menu present, restore option absent - exactly the symptom. This would be a 42.20.1 getText-strictness regression surfacing through us, not a bug in the mod's code. Strongest candidate; check the reporter's language first.
2. **Another mod's translation with a stray `%`.** Same mechanism, triggered by a co-installed mod. If that mod patches or is invoked during the mechanics menu build, our option can be collateral.
3. **Environment / false positive.** Stale cached mod copy, mod disabled after the update, or a conflict. Reporter states it is untested.

MP checksum changes (`NetChecksum` / anti-cheat, also in this hotfix) are an unlikely cause - they would kick or fail to load the whole mod, not selectively drop one context-menu option.

## Verification

English SP on 42.20.1, developer's machine, 2026-08-05: mod works normally. The restore option appears on a sub-100% engine and is correctly hidden only when quality is already 100% (expected - `engineQuality < 100` guard at `REQ_ISVehicleMechanics.lua:67`). `Logs\2026-08-05_17-53_DebugLog.txt` and `console.txt` show `loading Ivmakk_RestoreEngineQuality` plus its two EN translation overrides and **no** REQ errors, no `getText`/`IllegalFormatException`, nothing referencing `doPartContextMenu`. The only ERROR lines are baseline vanilla noise (tiledef file-number ranges, FluidContainer whitespace-name sanitising, mannequin-zone properties, duplicate/invalid room metaIDs) - all present regardless of this mod.

English MP (dedicated server) on 42.20.1, same day: also tested working - the restore option appears and the restoration completes, matching the SP result. So the report is not an SP-vs-MP split either.

Ukrainian SP on 42.20.1, same day: also tested working, option appears. Relevant because the mod ships only EN translations, so on a UA client its own `IGUI_REQ_*` keys fall back to EN while the borrowed vanilla keys (`IGUI_perks_Mechanics`, `Tooltip_vehicle_keyRequired`, `IGUI_Vehicle_EngineQuality`) resolve to the game's UA files - which 42.20.1 re-escaped. UA passing means that specific non-English path is clean, so hypothesis 1 is partly tested: at least Ukrainian does not trip the getText strictness regression. It does not clear other languages, but it removes the simplest form of the hypothesis.

This confirms the static verdict: in English and Ukrainian, the mod's code path is clean on 42.20.1 (EN in SP + MP, UA in SP). The report is not a general 42.20.1 break; it points to something specific to the reporter's setup - a language whose vanilla files 42.20.1 missed, another mod's translation, or an environment issue.

## Repro plan

Per `pz-modding`'s debugging guide - enable `DEBUG_MODE` in `REQ_Utils.lua` first so the `pcall` around init stops swallowing traces, and watch `Logs\<timestamp>_DebugLog.txt`.

1. Reproduce in **English SP** on a fresh 42.20.1 save, mod-only: right-click the Engine in the mechanics UI, confirm whether the restore option appears. Expected from static analysis: it appears. If it does not, capture the DebugLog trace - that promotes this from "unreproduced" to a real mod bug.
2. If EN is clean, switch the game to the reporter's language (ask which) and repeat. A `getText`/`IllegalFormatException` trace pointing into `ISVehicleMechanics` or `validateAllRequirements` confirms hypothesis 1.
3. Ask the reporter for: game language, SP vs MP, full mod list, and the `<timestamp>_DebugLog.txt` from a run where the option was missing.

## Possible mitigation (only if a repro confirms a getText throw reaches our path)

If a borrowed vanilla key throws in some locale, guarding the mod's own `getText` calls will not help when the throw is inside the vanilla line-60 call. If the throw is inside our own steps (2/4), wrapping `validateAllRequirements` + `generateMenuText` so a getText failure still lets `addOption` run with a plain fallback label would keep the option visible. Do not add speculative guards before a repro shows which path actually throws.
